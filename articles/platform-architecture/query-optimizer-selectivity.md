# Query Optimizer Selectivity

**Query optimizer selectivity** is the rule set Salesforce uses to decide whether a filter narrows a query enough to
be served from an index. Because the multitenant architecture keeps the underlying database's own optimizer from
tuning tenant queries effectively, Salesforce runs its own optimizer in front of it for the queries generated by
SOQL, reports and list views.[^s2] The Apex Developer Guide defines a query as selective when a filter on an indexed
field brings the result below a system-defined threshold, and notes that two or more such filters perform better.[^s1]

## How the optimizer works

The optimizer is cost-based: it scores candidate execution paths using statistics about the org's data and picks the
cheapest plan.[^s5] It chooses the best index to drive the query when one qualifies, otherwise the best table to
drive it, then orders the remaining joins (including sharing joins) to minimize I/O.[^s2] Trailhead says most of its
statistics are gathered weekly and that pre-queries are cached hourly.[^s5] The optimizer's record counts include
Recycle Bin rows and records awaiting physical delete, so a large soft delete can make a filter look selective when
it is not; hard deletes through Bulk API avoid that distortion.[^s6]

## The thresholds

The Large Data Volumes guide publishes the percentages the optimizer checks before using an index:[^s3]

- **Standard indexes** qualify when the filter matches under 30% of the first million records and under 15% of
  records beyond that.[^s3]
- **Custom indexes** qualify when the filter matches under 10% of the first million records and under 5% beyond that.[^s3]

Salesforce's engineering blog adds caps of one million targeted records for standard indexes and 333,333 for custom
indexes.[^s6] The current Apex guide gives the simpler rule of thumb that a filter on an indexed field should match
under 10% of rows, and states that a CONTAINS scan over 333,333 rows will not use an index; it warns these thresholds
can change.[^s1] For compound filters, AND conditions use their indexes unless one of them returns more than 20% of the
object's records, while OR conditions need every field indexed and fall back to a scan only if all return more than
10%; LIKE filters skip the statistics table and sample up to 100,000 records instead.[^s3]

## What is indexed

By default Salesforce indexes Id, Name, OwnerId, lookup and master-detail foreign keys, CreatedDate, SystemModstamp,
RecordType fields, and custom fields marked External ID or Unique; Support can add custom indexes, and the optimizer
may index other fields automatically.[^s1] Custom indexes are not possible on long or rich text areas, encrypted
text, multi-select picklists, currency fields in multicurrency orgs, non-deterministic formulas (for example ones
using TODAY or NOW or cross-object references), and certain standard fields such as Opportunity Amount and Lead
Status.[^s3] Index tables exclude null rows by default, so filtering on blanks needs a Support-built index that
includes nulls; two-column indexes can help list views that filter on one field and sort on another.[^s3]

## Common non-selective patterns

Negative operators (`!=`, NOT CONTAINS, NOT STARTS WITH) and comparisons with an empty value usually prevent index
use.[^s1] Leading wildcards such as `LIKE '%smi%'`, null checks and range comparisons on text fields are also flagged
as non-selective, and Trailhead recommends SystemModstamp over the unindexed LastModifiedDate.[^s5] Salesforce's
older guidance suggests rewriting negations as `=` or `IN` with the complementary values, and replacing
non-deterministic formulas with an indexed field populated by automation.[^s6]

## Diagnosing queries

The Developer Console Query Plan tool, enabled under Help > Preferences, shows whether a query would use an index or a
TableScan; it does not evaluate SOSL.[^s5] The REST API's `explain` parameter on the Query resource returns the same
kind of feedback for a query, report or list view without running it: candidate plans ordered from cheapest, each
with a `leadingOperationType` such as Index or TableScan, a `relativeCost`, cardinality figures and notes such as
filters ignored because they are unindexed. The feature is documented as beta.[^s4]

## Connections

Selectivity is a core technique within **large data volumes** design and a direct consequence of **multitenancy**,
which rules out tenant-level database tuning.[^s2] It governs how **SOQL** filters perform, and the same Apex guide pairs it with **Batch Apex** as the
preferred way to process very large result sets for mass updates.[^s1] **External ID fields** are one of the cheapest ways to get an index.[^s3] **Skinny
tables** complement indexes when joins rather than filters are the bottleneck, and **data skew** inflates the counts
that make filters fail their thresholds.[^s2][^s6] The **REST API** exposes the explain plan.[^s4]
