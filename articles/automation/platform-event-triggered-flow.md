# Platform Event-Triggered Flow

A platform event-triggered flow is a Flow Builder flow whose Start element names a platform event instead of an object, a schedule or a screen; every event message delivered to it launches a new flow interview.[^s1][^s4] It is the declarative subscriber on the Salesforce event bus: Apex, the APIs, other flows and external systems publish messages, and the flow reacts to them in the background without any user interaction.[^s3] The Admins blog lists typical uses such as opening a case when a monitored device reports a dangerous reading, flagging an account and emailing the customer when an appliance needs service, reordering supplies when a printer runs low, and logging errors from screen flows that failed without a fault path.[^s3]

## How it works

You create the platform event and its custom fields first, then choose **Platform Event-Triggered Flow** in the new-flow dialog and select the event in the Start element.[^s3] Inside the flow, the `$Record` global variable holds the incoming message's field values, so Decision, Get Records, Create Records and other elements can branch and act on them.[^s1][^s3][^s4]

Execution is decoupled from the publisher. The flow runs asynchronously in a separate transaction from the one that published the event, so there can be a short delay between publishing and processing.[^s1][^s3] Messages are evaluated in the order received, by replay ID; a flow can receive up to 200 messages in a batch, order is kept within each batch, and one batch can mix messages from several publishers.[^s1] Debug logs for these interviews are written under the **Automated Process** user, yet each interview runs in the context of the user who published the event, so records it creates or updates show that publisher in `CreatedById` and `LastModifiedById`.[^s1] That differs from a platform event Apex trigger, which runs as the Automated Process entity unless its running user is overridden through `PlatformEventSubscriberConfig`.[^s4]

Flows can also consume events a second way: a **Pause** element in an autolaunched flow subscribes a running interview to a platform event and resumes it only when an incoming message matches the conditions you define, optionally storing the message in a record variable.[^s1][^s4] That is a wait-for-a-signal pattern inside a longer flow; the platform event-triggered flow is the start-on-every-message pattern.[^s1]

## Limits and gotchas

- **No ordering across subscribers.** Flows, paused interviews and processes subscribed to the same event are not processed in any guaranteed order relative to one another.[^s1]
- **Silent failures.** If an event fails, the flow doesn't start and no flow error email is sent; troubleshoot through errors generated by the platform event itself.[^s1]
- **No subflows.** A platform event-triggered flow can't call another flow through the Subflow element.[^s2]
- **Event references.** You can't use an event reference to set a flow record variable or an Apex sObject variable; map each event field to an input variable instead.[^s2] Email alerts can't use event values directly, so the documented workaround is an autolaunched flow with input variables.[^s2]
- **Infinite loops.** A flow that publishes the same event it subscribes to can loop until limits are hit; make sure the new message's values don't match the criteria that trigger the flow.[^s2][^s3]
- **Subscription management.** Flows appear in the event's Subscriptions related list, but you can't manage (suspend, resume or reset) their subscriptions there.[^s4]
- **Packaging.** Before uninstalling a package that contains the event, delete interviews waiting on it; the associated object isn't packaged automatically with an event process.[^s2]
- **Supported events.** Flows can subscribe to custom platform events and a short list of standard events, including `BatchApexErrorEvent` and `FlowExecutionErrorEvent`.[^s2]

## When to use it (and when not)

Choose a platform event-triggered flow when an admin-owned automation must react to a signal rather than to a record change: messages from an external system, IoT or device data, or events your own code publishes to hand work off.[^s3] A common pattern splits a transaction to avoid `MIXED_DML_OPERATION` errors: a record-triggered flow publishes an event, and the event-triggered flow performs the update on the other object type in its own transaction.[^s3] If the trigger is a change to a Salesforce record, a record-triggered flow is simpler; if processing needs code-level logic, a specific running user or subscription management from the Subscriptions related list, a platform event Apex trigger gives more levers.[^s1][^s4]

## Connections

It is one of the flow types built in **Flow Builder** and part of the broader **process-automation** toolset, alongside the **record-triggered flow**, the **schedule-triggered flow** and the no-trigger **autolaunched flow**, which is also the host for Pause-based event subscriptions.[^s1][^s3] It **depends on** **platform events** and is a declarative **alternative to Apex triggers** subscribed to the same channel.[^s4] Because failed events don't start the flow or send flow error emails, **flow fault handling** and event-error monitoring matter.[^s1] It is the low-code entry point to **event-driven architecture** on the platform.[^s3]
