# Transform Element

The **Transform element** is a Flow Builder element that copies values from one or more source resources (single
values or collections, including screen components) into an autogenerated target variable and shapes those values on
the way.[^s1] Instead of walking a collection item by item, the builder draws mappings between source fields and
target fields, and the element produces the whole output at once.[^s1][^s2]

## How it works

A Transform has three parts: **source data**, **target data** and **mappings**.[^s1][^s2] The source is any flow
resource, for example the `selectedRows` of a data table on a screen. The target is a new resource whose data type
you choose, such as Text, Number, a Record type or an Apex-defined type, with "Allow multiple values (collection)"
selected when the output should be a collection.[^s2][^s3] Mapping is done on the canvas: hover a source field, click
its connector, then click the Map icon on the target field.[^s2] A target field can also be set by a formula or a
static value rather than a direct field mapping, and the output collection holds only the fields you mapped.[^s1]

Common shapes of transform:

- **Extract** a field into a simple collection, such as record Ids into a text collection for an `In` filter.[^s2]
- **Reshape** selected rows into a record collection that an Update Records element can save.[^s1]
- **Aggregate** a collection into one Number field with the Count or Sum aggregate type.[^s3]
- **Join** two collections on a shared key field into one combined output collection.[^s4][^s5]

The Ids case exists because the `In` operator in data elements accepts only collections of simple values, not record
collections, so a Transform converts records into a list of Ids first.[^s2] For aggregation, you map the source
collection to a Number target field, pick Count or Sum, and for Sum choose the source field to add up.[^s3] Salesforce
Help's example uses one Transform to count locations returned by an external system and a second to total their
employees.[^s3]

## Limits and gotchas

- Aggregation can only write to a Number target field; a target field without a Map button cannot be mapped.[^s3]
- For aggregation, the source and target fields must sit at the same level of nesting in their resources.[^s3]
- A screen component value can't be mapped straight to a field; use a formula, and click Check Syntax again after editing.[^s1]
- The transform's output collection doesn't appear under Record Collection Variables in the Toolbox.[^s1]
- Joins keep only inner-join matches, so a record with no partner in the other collection is dropped.[^s4]

Salesforce Ben reports further practical limits: mapping supports one nested collection per transformation, an
Apex-defined resource can reference up to 10 levels of nested fields, formula expressions inside the element are
capped at 255 characters, and debug details show at most 20 records of a collection.[^s5] Treat these as
practitioner-reported rather than documented limits and confirm them in your org.

## When to use it (and when not)

Trailhead's guidance is to use a Transform whenever it can do the job and fall back to a Loop only when it can't; the
module describes Transforms as roughly ten times faster than loops doing the same work and better at scale.[^s1] A
Loop is still the right tool when each item must go through its own series of elements, such as a per-user
action.[^s1] Avoid placing Update Records inside a loop: each execution consumes a query, and the flow can hit the
limit after relatively few iterations.[^s1] For joins, a Transform replaces nested loops, which the Salesforce Time
write-up calls costly on governor limits and poor at scaling.[^s4] Sometimes several Transform configurations solve
the same problem, and choosing between a Transform and a record-collection approach can be a matter of
preference.[^s1][^s2]

## Connections

The Transform element is part of `kt:flow-builder` and appears in Trailhead's `kt:screen-flow` examples, where it maps
data table selections, and it is equally relevant to the background logic of an `kt:autolaunched-flow`.[^s1] It is an **alternative to** the `kt:flow-loop-element` for bulk reshaping
and is a core technique of `kt:flow-bulkification`, because moving data operations out of loops keeps flows within
`kt:governor-limits`.[^s1][^s4] It **depends on** `kt:apex-defined-types` when the target is a custom structure, such
as the generic data-table row class used to display joined results.[^s3][^s4] It pairs with `kt:flow-http-callout`,
whose responses can be counted, summed or reshaped in a Transform.[^s3] It is distinct from Data Cloud's
`kt:data-transforms`: both reshape and join data, but the Transform element works on flow resources inside a single
flow.[^s1][^s5]
